# Spec-Driven Development — Agent Workflow and Prompts

## 1. Overview

This document contains the agents defined and executed during the Customer feature validation process for the .NET 8 project.

The workflow evolved from:

```text
Specify → Plan → Tasks → Implement → Converge
```

to the improved workflow:

```text
Specify → Clarify → Plan → Tasks → Implement → Converge
```

**Clarify** was proposed later and was not executed in the original five-agent package.

# 3. Spec Kit Specify

**Agent:** `speckit-specify`

### Objective

Transform a business requirement into a precise, testable and implementation-independent specification.

### Prompt Used

```text
Create a Customer feature for the .NET 8 CustomerApi.

A customer has an Id, FirstName, LastName, Email and CreatedAt.

The API must allow creating a customer and retrieving a customer by Id.

Email is required and must have a valid email format.

FirstName and LastName are required.

A customer cannot be created with a duplicate email.

Creating a customer returns HTTP 201.

Retrieving an existing customer returns HTTP 200.

Retrieving a nonexistent customer returns HTTP 404.

Invalid customer data returns HTTP 400.

The feature should be covered by automated tests.
```

### Expected Artifact

```text
specs/001-customer/spec.md
```

### Responsibilities

- Define WHAT and WHY.
- Define functional requirements.
- Define business rules.
- Define non-functional requirements.
- Define acceptance criteria.
- Define edge cases.
- Define assumptions.
- Identify Open Questions.

Typical identifiers:

```text
FR-###   Functional Requirement
BR-###   Business Rule
NFR-###  Non-Functional Requirement
AC-###   Acceptance Criterion
EC-###   Edge Case
```

Specify should not prematurely define controllers, repositories, EF Core, SQL Server, or other implementation details unless they are explicit constraints.

# 4. Spec Kit Clarify

**Agent:** `speckit-clarify`

### Status

**Proposed but not executed in the original workflow.**

The need for this agent was identified after reviewing the `Open Questions` generated by Specify.

### Objective

Resolve ambiguity before technical planning.

### Proposed Prompt

```text
Review the current feature specification and identify all unresolved 
or ambiguous decisions that could affect business behavior, API contracts, 
security, architecture, implementation or testing.

For each open question:

1. Identify the ambiguity.
2. Explain its impact.
3. Determine whether it is blocking for the technical plan.
4. Present the question to the stakeholder without inventing an answer.
5. Record the stakeholder's decision.
6. Update the specification with the resolved decision.
7. Convert the decision into explicit requirements, business rules, 
   acceptance criteria or technical constraints as appropriate.

Do not make business or security decisions on behalf of the stakeholder.

The specification may proceed to Plan only when all blocking questions 
have been resolved.
```

### Responsibilities

```text
spec.md
   ↓
Open Questions
   ↓
Stakeholder Decisions
   ↓
Updated spec.md
   ↓
READY_FOR_PLAN
```

### Customer Open Questions

```text
OQ-001 — What HTTP status and response contract should be used when
creation is rejected because the email already exists?

OQ-002 — Is email uniqueness case-sensitive or case-insensitive?

OQ-003 — What exact email-validation standard and normalization
behavior should apply?

OQ-004 — Should whitespace-only names be considered missing values?

OQ-005 — Should invalid or malformed customer identifiers return
HTTP 400 or HTTP 404?

OQ-006 — What authentication mechanism and authorization policy
should apply?
```

# 5. Spec Kit Plan

**Agent:** `speckit-plan`

### Objective

Transform an approved specification into a technically coherent implementation plan.

### Prompt Used

```text
Create the technical implementation plan for the approved Customer specification. 
Inspect the existing .NET 8 repository and follow its architecture and conventions.
```

### Expected Artifact

```text
specs/001-customer/plan.md
```

### Responsibilities

Define HOW the requirements will be implemented:

- Architecture.
- Components.
- Domain/application responsibilities.
- Persistence.
- APIs.
- Security.
- Authorization.
- Error handling.
- Reliability.
- Observability.
- Testing.
- Configuration.
- Migrations.
- Deployment.
- Risks and trade-offs.

Technical decisions use:

```text
PD-###
```

# 6. Spec Kit Tasks

**Agent:** `speckit-tasks`

### Objective

Convert the specification and technical plan into executable, dependency-ordered implementation tasks.

### Prompt Used

```text
Generate dependency-ordered implementation tasks for the Customer feature 
using the approved specification and technical plan.

Ensure every requirement and acceptance criterion has traceable 
implementation and validation tasks.
```

### Expected Artifact

```text
specs/001-customer/tasks.md
```

### Task Convention

```text
T###
```

Each task should contain:

- Description.
- Requirement references.
- Acceptance criterion references.
- Technical decision references.
- Target component/file.
- Dependencies.
- Expected result.
- Validation criteria.

Example:

```markdown
## T003 — Implement Customer creation endpoint

Requirements:
- FR-001
- FR-004
- BR-001

Acceptance Criteria:
- AC-001
- AC-005

Depends on:
- T001
- T002
```

# 7. Spec Kit Implement

**Agent:** `speckit-implement`

### Objective

Implement approved tasks while preserving the specification, architecture, tests and project conventions.

### Prompt Used

```text
Implement the incomplete Customer feature tasks in dependency order.

Follow the specification, technical plan, tasks, constitution and shared contract.

Build and test the solution as you work.
```

### Responsibilities

1. Read specification.
2. Read technical plan.
3. Read task list.
4. Inspect repository.
5. Implement tasks in dependency order.
6. Add or update tests.
7. Build the solution.
8. Execute tests.
9. Fix implementation problems.
10. Validate completed tasks.

### Restrictions

Avoid:

- Unrelated refactoring.
- Speculative functionality.
- Unnecessary dependencies.
- Silent requirement changes.
- Weakening tests.
- Unjustified architecture changes.

### Output

```text
Specification
      +
Plan
      +
Tasks
      ↓
Source Code + Tests
```

# 8. Spec Kit Converge

**Agent:** `speckit-converge`

### Objective

Independently verify that the implementation satisfies the specification, plan, tasks and acceptance criteria.

### Prompt Used

```text
Audit the Customer feature against the constitution, specification, 
technical plan, implementation tasks, source code and automated tests.

Verify every requirement and acceptance criterion independently.

Do not implement fixes.
```

### Verification

Each requirement receives:

```text
PASS
PARTIAL
FAIL
NOT VERIFIED
```

Successful result:

```text
FR-001  PASS
FR-002  PASS
FR-003  PASS

AC-001  PASS
AC-002  PASS
AC-003  PASS

Build: PASS
Tests: PASS

Traceability: COMPLETE

Status: CONVERGED
```

Failure:

```text
Status: NOT_CONVERGED
```

---

# 9. Remediation Tasks

When Converge finds a genuine gap, it should create:

```text
RT###
```

Example:

```markdown
## RT001 — Fix customer not-found response

Type:
Remediation

Requirement:
FR-006

Acceptance Criterion:
AC-004

Problem:
The API returns HTTP 200 when the customer does not exist.

Expected:
HTTP 404 Not Found.

Validation:
Add or update an integration test covering a valid
but nonexistent customer identifier.
```

The remediation preserves traceability to the original requirement.

# 11. Authentication and Authorization Decision

During the Customer specification process, authentication and authorization were explicitly addressed.

## Authentication

Recommended mechanism:

```text
OAuth 2.0 / OpenID Connect
+
JWT Bearer access tokens
```

The identity provider should remain configurable. Microsoft Entra ID is an appropriate enterprise example.

## Authorization

Recommended mechanism:

```text
Policy-based authorization
```

Recommended permissions:

```text
Customer.Read
Customer.Write
Customer.Admin
```

| Operation | Permission |
|---|---|
| `GET /customers/{id}` | `Customer.Read` |
| `POST /customers` | `Customer.Write` |
| `PUT /customers/{id}` | `Customer.Write` |
| `DELETE /customers/{id}` | `Customer.Admin` |

Authentication failure:

```text
401 Unauthorized
```

Authenticated user without the required permission:

```text
403 Forbidden
```

The API should depend on capabilities/permissions rather than hard-coded provider-specific role names.

# 15. Package Status

The original generated package contains five physical custom agents:

```text
.github/agents/
├── speckit-specify.agent.md
├── speckit-plan.agent.md
├── speckit-tasks.agent.md
├── speckit-implement.agent.md
└── speckit-converge.agent.md
```

To implement the complete six-agent workflow, add:

```text
.github/agents/speckit-clarify.agent.md
```

and update the handoffs to:

```text
Specify → Clarify → Plan → Tasks → Implement → Converge
```

with the remediation loop:

```text
Converge → Implement → Converge
```
